# Grim Protocol — правила старта и рабочий протокол разработки

## 1. Назначение документа

Этот файл фиксирует правила будущей реализации Grim Protocol в режиме управляемой AI-разработки.

Цель процесса: сделать технически рабочий Unreal Engine RTS prototype с минимальным количеством ручной работы в Unreal Editor и максимальным количеством реализации через код, документацию и проверяемые маленькие этапы.

Визуальное качество, дизайн, финальные ассеты, красивая карта и UI-polish на этой стадии не являются целью. Мы строим техническую основу.

---

## 2. Роли

### 2.1. ChatGPT — техлид / координатор

ChatGPT отвечает за:

- контроль общего плана разработки;
- чтение текущей документации и состояния репозитория перед постановкой задач;
- выбор одного следующего этапа разработки;
- подготовку точного промпта для Cursor;
- разделение задач между Cursor и оператором Unreal Editor;
- проверку отчета Cursor после каждого этапа;
- проверку diff / измененной документации / текущего статуса в репозитории;
- принятие или отклонение этапа вместе с оператором;
- запрет перехода к следующему этапу, пока текущий не закрыт;
- предотвращение scope creep: Cursor не должен делать больше, чем задано в текущем этапе.

ChatGPT не пишет код напрямую, если код должен делать Cursor в рамках рабочего процесса. Исключение — подготовка документации, правил, task prompts и ревью.

### 2.2. Cursor + Composer — кодер / исполнитель

Cursor отвечает за:

- выполнение только той задачи, которая дана техлидом;
- чтение указанных документов перед изменениями;
- изменение C++ / Config / Docs / Tests в пределах текущего этапа;
- запуск доступных build/check команд, если окружение позволяет;
- исправление compile errors в пределах текущего этапа;
- обновление документации по результату работы;
- запись отчета о выполненном этапе в проектный лог;
- остановку после завершения этапа.

Cursor не должен:

- самостоятельно выбирать следующий этап;
- делать несколько задач одновременно;
- менять архитектуру без явного указания;
- добавлять визуальный polish;
- создавать лишние системы “на будущее”;
- массово переписывать существующий код без согласования;
- трогать `Binaries/`, `Intermediate/`, `Saved/`, `DerivedDataCache/`, generated files.

### 2.3. Пользователь — Unreal Editor operator / тестер

Пользователь отвечает за:

- локальное открытие проекта в Unreal Editor;
- сборку проекта;
- выполнение ручных действий в Unreal Editor;
- создание минимальных Blueprint/DataAsset/Level assets, если это необходимо;
- запуск PIE/playtest;
- проверку фактического поведения;
- передачу техлиду результатов проверки, ошибок, логов, скриншотов;
- финальное подтверждение, что этап принят с точки зрения поведения в Editor.

Пользователь не должен вручную программировать системы, если это можно сделать кодом через Cursor. Ручная работа в Editor допускается только там, где это реально требуется Unreal workflow.

---

## 3. Главный принцип процесса

Работа идет строго по одному этапу.

```text
Один этап → код → документация → сборка → ручная проверка в Editor → ревью → принятие → следующий этап
```

Следующий этап запрещен, пока текущий не принят двумя сторонами:

1. ChatGPT подтверждает архитектурную и процессную приемку.
2. Пользователь подтверждает локальную проверку в Unreal Editor.

Если хотя бы одна сторона не принимает этап, этап остается открытым, и Cursor получает fix prompt.

---

## 4. GitHub и репозиторий

Репозиторий будет публичным, чтобы ChatGPT мог читать его состояние перед постановкой задач и после каждого этапа.

### 4.1. GitHub используется для

- истории изменений;
- хранения документации;
- фиксации принятых этапов;
- отчетов Cursor;
- контроля текущего статуса;
- синхронизации между участниками процесса.

### 4.2. Локальная среда остается основной

Основная разработка и проверка Unreal происходят локально:

```text
Cursor локально пишет код
↓
пользователь локально собирает проект
↓
пользователь проверяет в Unreal Editor
↓
если принято — commit / push
↓
ChatGPT проверяет GitHub и дает следующий этап
```

Нельзя считать этап принятым только потому, что Cursor сделал commit. Unreal-проект считается рабочим только после локальной сборки и проверки в Editor.

---

## 5. Обязательное правило проверки репозитория

Перед постановкой новой задачи ChatGPT должен проверить актуальное состояние репозитория:

- README / CONTRIBUTING / STYLE;
- Docs/Development;
- текущий task-list;
- AI/project log;
- последние commits или измененные файлы, если доступно;
- статус текущего этапа.

После каждого этапа ChatGPT должен проверить:

- что Cursor обновил документацию;
- что отчет по этапу записан;
- что scope не расширен;
- что нет перехода к следующему этапу без разрешения;
- что измененные файлы соответствуют задаче;
- что для пользователя есть понятный список ручных Unreal Editor steps.

Если GitHub временно недоступен, ChatGPT должен явно сказать, что не может проверить репозиторий, и запросить у пользователя отчет Cursor / diff / файлы вручную.

---

## 6. Что делаем на этой стадии

Цель текущей стадии — технический RTS prototype.

Фокус:

- C++ architecture;
- GAS foundation;
- camera control;
- unit selection;
- basic command system;
- unit movement;
- resource loop;
- basic building/unit definitions;
- minimal HUD for technical feedback;
- multiplayer-ready/server-authoritative design where applicable;
- automated or manual validation notes.

---

## 7. Что не делаем на этой стадии

На технической стадии не делаем:

- финальный визуальный дизайн;
- красивую карту;
- narrative content;
- production UI art;
- VFX polish;
- sound design;
- cinematic systems;
- campaign content;
- complex terrain;
- декоративные ассеты;
- баланс как финальный продукт.

Рабочее поле — плоская тестовая карта с минимальным количеством элементов.

Допустимый уровень визуала:

- плоскость;
- простые primitives/placeholders;
- базовые материалы;
- минимальные icons/text labels;
- debug drawing;
- минимальный HUD только для проверки систем.

---

## 8. Правило “кодом, если можно кодом”

Все, что можно сделать кодом без потери надежности Unreal workflow, делается кодом.

Через код желательно делать:

- gameplay classes;
- components;
- replication/RPC;
- GAS classes;
- definitions/structs;
- config defaults;
- debug visualization;
- validation helpers;
- minimal test actors;
- technical HUD data flow.

Через Editor вручную допускается делать:

- создание test level;
- placement минимальных actors;
- Blueprint child от C++ class, если это быстрее и надежнее;
- назначение mesh/material placeholders;
- создание Data Assets, если автоматизация еще не готова;
- проверка PIE;
- настройка input/map defaults, если кодом это неудобно или рискованно.

Любая ручная Editor-задача должна быть явно указана Cursor в отчете и техлидом в списке задач для пользователя.

---

## 9. Размер одного этапа

Один этап должен быть маленьким и проверяемым.

Нормальный размер этапа:

- 1 система или 1 foundation slice;
- 3–10 файлов, если возможно;
- четкие acceptance criteria;
- понятный manual test;
- без визуального polish;
- без внедрения следующей системы.

Плохой этап:

- “сделай всю RTS camera + selection + movement + resources”;
- “реализуй базовую игру”;
- “сделай все по документации”;
- “сам выбери следующие задачи и продолжай”.

---

## 10. Обязательный формат задачи для Cursor

Каждая задача Cursor должна содержать:

1. Название этапа.
2. Документы, которые нужно прочитать.
3. Конкретную цель.
4. Scope.
5. Out of scope.
6. Файлы/области, которые можно менять.
7. Файлы/области, которые нельзя менять.
8. Acceptance criteria.
9. Build/check commands, если применимо.
10. Требование обновить документацию и project log.
11. Требование остановиться после этапа.

Cursor всегда должен завершать работу отчетом.

---

## 11. Обязательный отчет Cursor после этапа

Cursor должен обновлять файл:

```text
Docs/Development/AI_Project_Log.md
```

Если файла нет — создать его.

Формат записи:

```md
## YYYY-MM-DD — <Task ID / Task Name>

Status: NEEDS_REVIEW / BLOCKED / DONE_CANDIDATE

### Files changed
- ...

### What was done
- ...

### What was intentionally not done
- ...

### Build / validation
- Command run: ...
- Result: Passed / Failed / Not run
- Notes: ...

### Manual Unreal Editor steps for operator
1. ...
2. ...

### Acceptance checklist
- [ ] Compiles
- [ ] Unreal Editor opens
- [ ] PIE starts
- [ ] Feature behavior verified
- [ ] Multiplayer PIE checked, if relevant

### Risks / open questions
- ...

### Stop condition
Stopped after this task. Awaiting review by tech lead and operator.
```

Cursor также должен обновить соответствующий task-файл, если он существует.

---

## 12. Формат задач для пользователя после этапа

После Cursor-этапа ChatGPT дает пользователю отдельный список ручных действий.

Формат:

```text
Твои действия в Unreal Editor:
1. ...
2. ...
3. ...

Что проверить:
1. ...
2. ...

Что прислать обратно:
1. Compile result
2. PIE result
3. Screenshot/log/error, если есть
```

Список должен быть коротким и практическим. Не давать пользователю длинные теоретические инструкции.

---

## 13. Правила приемки этапа

Этап считается принятым только если:

- Cursor выполнил задачу в пределах scope;
- документация обновлена;
- project log обновлен;
- нет очевидного архитектурного нарушения;
- проект компилируется или есть явно принятая причина, почему compile не запускался;
- пользователь выполнил нужные Editor steps;
- PIE/manual test прошел или результат признан достаточным для текущего этапа;
- ChatGPT сказал, что этап принят;
- пользователь подтвердил, что этап принят.

Если compile failed — этап не принят, кроме случаев, когда задачей был audit или подготовка документации без code changes.

---

## 14. Правила отказа от этапа

Этап возвращается Cursor на исправление, если:

- scope расширен;
- сделаны лишние системы;
- нарушена архитектура проекта;
- код не компилируется;
- нет отчета;
- не обновлена документация;
- нет manual Editor steps;
- фича не проверяется на плоском тестовом поле;
- Cursor перешел к следующему этапу сам;
- изменения слишком большие и плохо контролируемые.

В этом случае ChatGPT дает fix prompt, а не новый feature prompt.

---

## 15. Технические ограничения проекта

Базовые правила разработки:

- Unreal Engine 5.8.1.
- C++ first.
- Blueprint только для UI, Editor workflow, tuning и минимальных asset bindings.
- GAS-first там, где это связано с атрибутами, эффектами, способностями, уроном.
- Multiplayer-first / server-authoritative design.
- Data-driven-first: баланс и definitions не хардкодить в C++.
- Не использовать Lyra architecture как основу.
- Project symbols должны иметь префикс `GP`.
- Не использовать magic strings для Gameplay Tags.
- Не делать визуальный polish в technical stage.
- Не коммитить generated/intermediate/cache files.

---

## 16. Рекомендуемая структура веток

Минимальная схема:

```text
main — стабильное принятое состояние
feature/<task-id-short-name> — текущий этап
```

Пример:

```text
feature/gp-s04-asc-subclass
feature/gp-0201-rts-camera
feature/gp-0202-selection
```

Пушить в GitHub желательно после локальной проверки. Для обмена отчетами Cursor может пушить feature branch, но `main` должен оставаться стабильным.

---

## 17. Стартовый порядок работы

Перед первой реализацией:

1. Сделать репозиторий публичным или обеспечить ChatGPT доступ к чтению.
2. Проверить `.gitignore` для Unreal.
3. Проверить Git LFS для `.uasset`, `.umap` и крупных ассетов.
4. Убедиться, что Cursor открывает корень репозитория, а не только папку `GP`.
5. Убедиться, что Unreal открывает `GP/GP.uproject`.
6. Сделать baseline compile.
7. Создать/проверить `Docs/Development/AI_Project_Log.md`.
8. Определить текущий официальный NEXT task из документации.
9. Только после этого давать первый implementation prompt.

---

## 18. Рабочее поле для тестов

На технической стадии используется минимальный test level:

- flat plane;
- default lighting;
- PlayerStart;
- NavMeshBoundsVolume, если нужен movement;
- несколько placeholder units;
- несколько placeholder resource/building actors;
- без художественной карты.

Карта нужна только как test harness. Она не является production map.

---

## 19. Коммуникационный протокол

После каждого этапа пользователь присылает ChatGPT:

```text
1. Ссылку на commit/branch или сообщение, что изменения запушены.
2. Отчет Cursor из AI_Project_Log.md.
3. Результат compile.
4. Результат проверки в Unreal Editor.
5. Ошибки/логи/скриншоты, если есть.
```

ChatGPT после этого:

```text
1. Проверяет репозиторий.
2. Сравнивает результат с задачей.
3. Решает: принять / вернуть на fix / откатить / запросить уточнение.
4. Если принято — дает следующий prompt.
```

---

## 20. Главная защита от хаоса

Cursor не управляет проектом.

Cursor выполняет конкретный этап.

Техлид управляет последовательностью.

Пользователь подтверждает реальную работоспособность в Unreal Editor.

Никакой следующий этап не начинается без явного решения:

```text
Этап принят. Переходим к следующему.
```

---

## 21. Risk-Based Development Workflow

Canonical validation selection (which contracts / builds to run) lives in:

`Docs/Development/Risk_Based_Development_Workflow.md`

Default for a bounded slice: slice contract + 3–5 affected regressions, not the full project suite. Full suite only when the change risk justifies it. Docs-only stages run no Unreal tests or builds. Factual review before operator test, before merge, and after merge is unchanged.
